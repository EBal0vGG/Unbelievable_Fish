# Платёжные правила системы

Документ фиксирует **обязательные правила** домена оплаты и биллинга для платформы Fish Exchange.  
При дальнейшей разработке (backend, frontend, миграции, события, API) изменения в денежной логике **должны соответствовать** этому файлу. Если требуется отклонение — сначала обновите этот документ и зафиксируйте решение (например, ADR).

**Область:** этап 1 — правила модели денег, депозитов, ledger, комиссии, инвойсов и поведения UI на уровне требований. Реализация может вводиться поэтапно, но **семантика** операций не должна противоречить нижеизложенному.

---

## 1. Общая модель денег

- У каждой **компании** есть внутренний учётный баланс (ledger view), не путать с физическими деньгами.
- Два показателя на счёте:
  - **`available`** — доступные средства (можно использовать для новых ставок / оплат).
  - **`held`** — замороженные средства (резервы под депозиты, комиссии, обязательства по сделкам — по мере внедрения).
- **Физические деньги** находятся у платёжного провайдера / банка; в PostgreSQL хранится **учётная модель (ledger)**, а не «касса».

---

## 2. Валюта

- На первом этапе система работает в **одной валюте**: `currency = RUB`.
- Технически полезно хранить валюту явно (например, `Currency string`), но **мультивалютность не вводить**.
- **Правило:** один аукцион, одна сделка, один счёт/операция в рамках описанной модели — **только одна валюта** (сейчас RUB).

---

## 3. Деньги только в минимальных единицах

- **Не использовать `float64`** для денежных сумм.
- **Правильно:** целочисленный тип (например, `int64`).
- **Соглашение проекта (этап 1):** условно **без копеек** — например, `1000` означает **1000 рублей** (минимальная единица = 1 рубль, если не оговорено иначе в будущем).

---

## 4. Пополнение баланса (top-up)

Поток:

1. Компания создаёт заявку на пополнение (**TopUp created**).
2. Оплата через внешнего провайдера.
3. Провайдер подтверждает платёж.
4. **Billing** зачисляет средства на счёт.

**Правила:**

- Баланс **увеличивается только после подтверждения** платежа провайдером, **не** в момент нажатия кнопки в UI.
- **`TopUpCreated`** **не** меняет `available` / `held`.
- **`TopUpConfirmed`** увеличивает **`available`** (и при необходимости отражается в ledger).

**Пример:** до подтверждения `available = 0`, `held = 0`; после подтверждения top-up на 100 000: `available = 100 000`, `held = 0`.

---

## 5. Ставка и депозит (не полная сумма ставки)

- Для B2B-аукциона участие обеспечивается **депозитом**, а не полной суммой ставки.
- Полная сумма сделки оплачивается **позже**, после победы и контракта (отдельный **invoice**, см. раздел 14).
- Если компания делает ставку `bid = 1 000 000`, на балансе **не требуется** весь миллион; требуется **обеспечение депозитом** по правилам аукциона.

---

## 6. Размер депозита

- **Депозит = 5% от стартовой цены аукциона** (`start_price`).
- Депозит **фиксируется на уровне аукциона** и **не растёт** при последующих ставках (в том же аукционе).

---

## 7. Депозит считается по стартовой цене; один резерв на пару (аукцион, компания)

- При **первой успешной ставке** компании в данном аукционе резервируется:  
  `deposit = auction.startPrice * 5%` (в минимальных единицах, согласно разделу 3).
- При **следующих ставках** той же компании в **том же** аукционе **новый депозит не резервируется**.
- Пример: `startPrice = 100 000` → `deposit = 5 000`; последующая ставка `1 000 000` возможна при уже замороженных **5 000** под этот аукцион.

**Хранение:** отдельная сущность/таблица **`auction_deposits`** (или эквивалент):

| Поле         | Назначение                          |
|-------------|--------------------------------------|
| `auction_id`| Аукцион                              |
| `company_id`| Компания-участник                    |
| `amount`    | Сумма депозита (целое)               |
| `status`    | См. ниже                             |

**Статусы депозита:**

- **`HELD`** — заморожен.
- **`RELEASED`** — возвращён на доступный баланс (через ledger).
- **`CAPTURED`** — удержан (штраф / зачёт в пользу платформы и т.д. — по сценарию).

**Зачем отдельно:** не рост депозита, возврат проигравшим, удержание при отказе, зачёт комиссии.

**Уникальность:** `UNIQUE (auction_id, company_id)` — **один аукцион + одна компания = один депозит**; защита от повторного резерва в том же аукционе.

Если запись уже есть со статусом **`HELD`**, при новой ставке в том же аукционе **повторно не резервируем**.

---

## 8. Ставка может быть больше `available`, но не без депозита

- Ставка по сумме **может** превышать текущий **`available`**, если это допускается бизнес-правилами торгов **и** выполнено условие по **депозиту** (заморозка / достаточность средств на **новый** депозит при первой ставке в аукционе).
- Проверка: **обеспечен ли депозит** (и не нарушены инварианты баланса из раздела 17).

---

## 9. Когда резервируется депозит (порядок в транзакции)

Депозит резервируется **после** успешной валидации ставки, **не** до неё.

**Правильный порядок (атомарно, одна транзакция):**

1. Заблокировать аукцион (lock).
2. `Auction.PlaceBid` — валидация ставки.
3. Вычислить требуемый депозит (если первой ставкой компании в этом аукционе — см. разделы 6–7).
4. Зарезервировать депозит (ledger + `auction_deposits`, если применимо).
5. Сохранить ставку.
6. Сохранить состояние аукциона.
7. Commit.

Если ставка **невалидна** — **деньги / депозит не трогаем** (нет частичного резерва до валидации).

---

## 10. После завершения аукциона: топ-N кандидатов и остальные

Аукцион возвращает **ранжированный список кандидатов-победителей** (rank 1, 2, 3, …).

**Правило:**

- **Топ-N кандидатов** (как определено политикой аукциона, минимум те, кто нужен для fallback): депозиты остаются **`HELD`** до финального исхода по сделке / цепочке победителей.
- **Остальные участники:** депозит **`RELEASED`** (возврат через ledger).

Обоснование: при отказе rank 1 право переходит к rank 2; rank 2 должен оставаться финансово обеспечен.

---

## 11. Rank 1 подтвердил сделку (покупку)

Если **rank 1** подтвердил:

- **Rank 1** становится фактическим покупателем.
- **Rank 2 / rank 3** (и прочие бывшие резервные кандидаты из топ-N): депозиты **`RELEASED`**.
- **Остальные** уже получили возврат по правилу раздела 10.

После подтверждения победителем:

- **Комиссия платформы** списывается **из депозита** победителя (см. раздел 13).
- **Остаток депозита** после комиссии возвращается победителю (через ledger).
- **Полная сумма сделки** оплачивается **отдельным invoice** (не «вся сумма из депозита»).

---

## 12. Отказ победителя (rank 1)

Если **rank 1** отказался:

- **Rank 1:** депозит удерживается как штраф — **`CAPTURED`** (проигравший платит платформе / штрафная модель этапа 1).
- **Rank 2** становится выбранным кандидатом (selected).
- **Rank 3** остаётся в резерве (pending в цепочке), с депозитом **`HELD`** по правилам топ-N.

Формулировка требования: при отказе победитель **теряет весь депозит** как штраф (отражение в ledger).

---

## 13. Комиссия платформы

- **`platformFee = 3%` от `finalPrice`** (целочисленно, согласованно с правилами округления проекта — зафиксировать в реализации явно).
- Комиссию платит **только фактический победитель** (тот, кто подтвердил сделку).
- **Когда списывать:** **после подтверждения** победителем сделки, **не** сразу после `AuctionWon`: первый кандидат может отказаться, комиссия должна относиться к **фактическому** победителю.

Событие типа **`PLATFORM_FEE_CAPTURED`** (или эквивалент в ledger) должно быть идемпотентно и привязано к подтверждению / сделке.

---

## 14. Полная оплата товара (invoice)

- Полную сумму товара **не** списывать с баланса целиком в момент ставки.
- Цепочка (логическая):

  `AuctionWon` → выбранный победитель подтверждает → `DealCreated` / подтверждения сделки →  
  `ContractPrepared` / `ContractSigned` → **`PaymentRequested`** → покупатель оплачивает **invoice** → **`DealPaid`**.

**Правило:**

- **Депозит** — для участия и ответственности (и частично под комиссию по сценарию).
- **Invoice** — для **полной оплаты товара** по сделке.
- **Просрочка оплаты invoice:** если инвойс не оплачен к `due_at`, он переводится в `EXPIRED`, сделка отменяется с причиной `PAYMENT_TIMEOUT`, **весь HELD депозит победителя по аукциону захватывается** (`CAPTURED`), winner selection переходит к следующему кандидату. Подробнее и обоснование политики: [ADR-0009](../decisions/ADR-0009-invoice-payment-timeout-forfeits-deposit.md).
- **Обязательство выплаты продавцу (Stage 12):** после оплаченного invoice и финализации winner selection в учёте появляется строка **`billing_seller_payouts`** со статусом **`PENDING`** на сумму **`goods_amount`** инвойса; до последующих этапов это **не** увеличение `seller.available` и не отдельная проводка «деньги у продавца» в ledger.

---

## 15. Кто получает деньги (типы потоков в ledger)

Три вида движения (концептуально; в ledger — отдельные типы проводок):

| Вид              | Смысл |
|------------------|--------|
| **Депозит**      | Пока у покупателя: `available → held` при резерве; обратно при `RELEASED`; иначе `CAPTURED` / зачёт комиссии по правилам. |
| **Комиссия платформы** | После подтверждения или сценария отказа: из **held** победителя / штрафных потоков → **выручка платформы** (отдельный счёт или агрегат в ledger). |
| **Оплата товара** | После invoice: платёж покупателя → **выплата / зачёт продавцу** (см. раздел 16). |

Технически в ledger это **разные операции** с разными `reference_type` / `reference_id`.

---

## 16. Выплата продавцу

- Продавец получает деньги **не** сразу после победы аукциона, а после оплаты по сделке.

**Базовый поток (первая версия):**

- `DealPaid` → **payout seller** (доступность средств продавцу по правилам ledger).

**Возможное усложнение позже:** `DealPaid` → подтверждение отгрузки → payout; для этапа 1 допускается упрощение «сразу после `DealPaid`», как согласовано в требованиях.

---

## 17. Инварианты баланса

- **`available >= 0`**, **`held >= 0`**.
- **Отрицательный баланс запрещён.** Ни одна операция не должна приводить к отрицательным `available` или `held`.

---

## 18. Все денежные изменения через ledger

Запрещено «тихо» делать только `UPDATE accounts SET available = available - 1000` без проводок.

**Каждое** изменение баланса оформляется записью в **ledger** с минимумом полей:

- `type` (тип операции),
- `amount`,
- `company_id` (и при необходимости контрагент / платформа),
- `reference_type`,
- `reference_id`,
- `created_at`.

**Примеры типов операций (этап 1, ориентир для именования):**

- `TOP_UP_CONFIRMED`
- `BID_DEPOSIT_RESERVED`
- `BID_DEPOSIT_RELEASED`
- `BID_DEPOSIT_CAPTURED`
- `PLATFORM_FEE_CAPTURED`
- `DEAL_PAYMENT_REQUESTED`
- `DEAL_PAYMENT_CONFIRMED`
- `SELLER_PAYOUT_CREATED`
- `SELLER_PAYOUT_COMPLETED`

Список может расширяться, но **принцип единый**: любое движение денег = проводка(и) в ledger.

---

## 19. Идемпотентность внешних платежей и webhooks

- Все внешние платежи и обработка событий провайдера должны быть **идемпотентными** (повтор webhook не приводит к двойному зачёту).
- Хранить и проверять, например: **`provider_payment_id`**, **`event_id`**, **`idempotency_key`**.
- Одна логическая операция не применяется дважды.

---

## 20. Что видит UI

Компания должна видеть:

- **`Available`**, **`Held`**, **`Total = available + held`**
- **Депозиты по аукционам** (по каждому аукциону отдельно, со статусом)
- **Историю операций** (ledger / выписка)
- **Инвойсы**
- **Комиссии**
- **Статус оплаты** по сделке

**Пример нескольких аукционов:**

- Участие в пяти аукционах → до пяти отдельных hold’ов в разрезе `auction_deposits`; **`held`** на счёте = сумма всех активных заморозок (согласованно с правилами статусов).

**Недостаточно `available` для нового депозита:**

- Пример: `available = 3 000`, требуемый депозит для **нового** аукциона = `5 000` → ставка отклоняется: **`ErrInsufficientFundsForDeposit`**.
- Средства, уже в **`held`** под другие аукционы, **нельзя** использовать повторно для нового резерва.

**После завершения аукциона (по каждому аукциону независимо):**

- Проигравшие (вне топ-N кандидатов) → депозит **`RELEASED`**
- Топ-N кандидатов → **`HELD`** до финала
- Победитель подтвердил → комиссия / capture остатка / возврат остатка по правилам разделов 11 и 13
- Победитель отказался → **`CAPTURED`** для отказника; перераспределение цепочки — раздел 12

**Важно:** депозит по аукциону A **не** смешивается с аукционом B; **`available`** — общий пул свободных денег; **`held`** — сумма обязательств по всем активным заморозкам; **`auction_deposits`** — детализация по аукционам.

## Краткая шпаргалка

| Тема | Правило |
|------|---------|
| Баланс | `available` + `held`, деньги «у провайдера», в БД — ledger |
| Валюта | Только RUB, явное поле, без мультивалютности |
| Суммы | Целые (`int64`), без float |
| Top-up | Только `TopUpConfirmed` увеличивает `available` |
| Ставка | Обеспечение депозитом 5% от `start_price`, не вся сумма ставки |
| Депозит на аукцион | Один раз на пару (auction, company), `UNIQUE`; не растёт со ставками |
| Резерв | После валидации ставки, в одной транзакции с сохранением ставки |
| После аукциона | Не-кандидаты: `RELEASED`; топ-N: `HELD` |
| Подтвердил rank 1 | Остальным кандидатам `RELEASED`; комиссия из депозита; остаток депозита назад; товар — invoice |
| Отказ rank 1 | Депозит `CAPTURED`; fallback по цепочке |
| Комиссия | 3% от `finalPrice`, только у фактического победителя, после подтверждения |
| Инвариант | `available >= 0`, `held >= 0` |
| Изменения | Только через ledger |
| Внешние события | Идемпотентность по ключам / id провайдера |
