# Отчёт о состоянии и интеграции системы «Рыбная биржа»

Документ для заказчика: фиксирует **связку трёх доменов**, **организацию процессов и слоёв**, **пошаговый путь от HTTP до чужих use case через outbox**, **карту событий**, **порядок эксплуатации** и **стек технологий**. Описание привязано к текущей реализации в репозитории.

---

## 1. Состав: три домена и как они соединены

Система разбита на три ограниченных контекста (домена), каждый со своей HTTP-службой и своей зоной ответственности:

| Домен | Назначение | HTTP-порт (по умолчанию) |
|--------|------------|---------------------------|
| **Catalog (Каталог)** | Товары (рыба, продукт), лоты, публикация лотов, отображение торговой информации по событиям из Trading | `8081` |
| **Trading (Торги)** | Аукционы, приём ставок, закрытие аукциона, определение победителя | `8082` |
| **Deals (Сделки)** | Проекции «аукцион → товар», выбор победителя, жизненный цикл сделки (подтверждение, контракт, оплата, отгрузка и т.д.) | `8083` |

**Физическое соединение доменов** реализовано так:

1. **Общая база данных PostgreSQL** — все службы используют один экземпляр БД (одна схема миграций).
2. **Паттерн Transactional Outbox** — при сохранении изменений домен записывает доменные события в таблицу outbox в той же транзакции, что и бизнес-данные. Это гарантирует согласованность «данные + событие».
3. **Служба `integration`** (отдельный процесс в Docker Compose, без внешнего HTTP) — циклически **забирает неотправленные сообщения из outbox**, десериализует их и передаёт во **внутреннюю шину событий** (in-memory bus в процессе `integration`). Подписчики на шине вызывают use case’ы **других** доменов (через те же репозитории/UoW к общей БД).

Итог: домены **не вызывают HTTP друг друга** для ядра процесса; связь идёт через **общую БД + outbox + процесс интеграции**.

## 2. Как организованы домены (код, процессы, «горутины»)

### 2.1. Структура модулей в репозитории (один домен — один пакет `internal/<домен>/…`)

У каждого домена типичное разделение слоёв:

| Слой | Папка | Роль |
|------|--------|------|
| Доменная модель | `internal/<домен>/domain` (или `…/deal`, `…/auction`) | Агрегаты, инварианты, FSM, типы доменных событий. Без БД и HTTP. |
| Прикладной слой | `internal/<домен>/app` | Use case’ы: загрузить агрегат → вызвать домен → сохранить → записать события в outbox. |
| Инфраструктура | `internal/<домен>/postgres` | Репозитории, unit of work, запись в `outbox_messages` внутри той же SQL-транзакции. |
| HTTP-адаптер | `internal/<домен>/http` (Trading, Deals) или обработчики в `cmd/catalog/main.go` (Catalog) | Разбор запроса → вызов одного use case → код ответа. |

**Роутеры:** у Trading и Deals — отдельные типы-роутеры в `internal/trading/http`, `internal/deals/http`. У Catalog маршруты зарегистрированы на `http.ServeMux` в `cmd/catalog/main.go`. Это не «три роутера в одном процессе», а **по одному HTTP-серверу на процесс** (см. ниже).

### 2.2. Процессы ОС / контейнеры (не один монолит)

В Docker Compose одновременно работают **четыре** Go-процесса, имеющие отношение к доменам:

| Процесс (`cmd/…`) | HTTP | Назначение |
|-------------------|------|------------|
| `catalog` | да (`:8081`) | Каталог |
| `trading` | да (`:8082`) | Торги (в API в первую очередь ставки) |
| `deals` | да (`:8083`) | Сделки |
| `integration` | **нет** | Outbox relay + in-memory шина + подписчики, вызывающие use case’ы всех трёх доменов |

Службы **catalog / trading / deals не подписаны на события** и **не запускают relay**. Они только обрабатывают входящие HTTP-команды (или, в случае каталога, внутренние методы сервиса) и пишут строки в БД и outbox.

### 2.3. Горутины: как устроен ввод-вывод

- В **каждом** HTTP-сервисе используется стандартный `net/http`: `ListenAndServe` блокирует основной поток, а **каждое входящее соединение** обрабатывается своей **горутиной** (поведение библиотеки Go). Отдельные пулы «по одному на домен» в коде не заводятся — модель «один процесс = один сервер = много горутин на запросы».
- В **`integration`**:
  - основной цикл в `main` крутит `Relay.RunOnce` с небольшим `Sleep` между итерациями;
  - отдельная **горутина** с `time.Ticker` периодически вызывает закрытие просроченных аукционов (`RunCloseExpired`).

Итого: **междоменная оркестрация не идёт через HTTP и не живёт в процессах catalog/trading/deals** — она сосредоточена в **одном** процессе `integration`, который читает общую таблицу outbox и синхронно вызывает зарегистрированные обработчики.

## 3. От HTTP-запроса до чужого use case: полный путь события

### 3.1. Шаг 1 — запрос попадает в домен-инициатор

Пример: `POST …/lots/{id}/publish` на Catalog.

1. HTTP-обработчик вызывает метод прикладного сервиса, например `CatalogService.PublishLot`.
2. Внутри вызывается **`TransactionManager.WithinTx`**: открывается **одна** SQL-транзакция.
3. В транзакции: загрузка лота и продукта, доменный метод `lot.Publish(…)` возвращает список доменных событий (в т.ч. `LotPublished`).
4. Сохранение изменённого лота в таблицы каталога.
5. **`outbox.Add`**: для каждого события вставляется строка в **`outbox_messages`** (тип вида `catalog.LotPublished`, JSON payload, `source_context`, метаданные). Вставка идёт через тот же `*sql.Tx`, что и сохранение лота.
6. **Commit** транзакции. До commit событие «снаружи» не видно; после commit HTTP-клиент получает ответ, а строка outbox гарантированно согласована с данными каталога.

Аналогично в Trading: `PlaceBid`, `PublishAuction`, `CloseAuction` выполняются внутри **`UnitOfWork.Do`** (своя транзакция): сохранение аукциона/ставок → `tx.Outbox().Add(…)` с событиями `trading.BidPlaced`, `trading.AuctionPublished`, `trading.AuctionClosed`, `trading.AuctionWon` и т.д.

### 3.2. Шаг 2 — доставка: только процесс `integration`

**Relay** (`internal/infra/outbox/relay.go`) в цикле:

1. Читает пачку неотправленных сообщений из `outbox_messages` (репозиторий в `internal/infra/outbox/postgres`: выборка с блокировкой строк, чтобы несколько воркеров не конфликтовали — при одном инстансе `integration` конкуренции нет).
2. Для каждой строки по полю `event_type` выбирается **decoder** (реестр в `integration/runtime.DefaultDecoders`) и JSON превращается обратно в типизированную структуру домена.
3. Собирается **`events.Envelope`** (тип, payload, время, meta: `company_id`, `user_id`, `correlation_id`, …).
4. Вызывается **`bus.Publish(ctx, envelope)`**.

### 3.3. Шаг 3 — in-memory шина и вызов чужих use case

**Шина** (`internal/infra/eventbus/inmemory/bus.go`) **синхронная**: для типа события она последовательно вызывает все зарегистрированные `handler(ctx, envelope)`. Это выполняется **в горутине relay-цикла**, не в фоновой очереди с отдельными воркерами.

Подписки задаются в `internal/integration/runtime/runtime.go` в `subscribeHandlers`:

- на `catalog.LotPublished` — один обработчик, который **последовательно** вызывает:
  - `tradingapp.CreateAuction.Execute` → `PublishAuction.Execute` (новые транзакции Trading, новые записи в БД и новые строки trading-outbox при публикации аукциона);
  - при необходимости `Catalog.AssignAuctionID` (снова транзакция каталога);
  - `dealsapp.CreateProjection.Execute` (проекция для сделок).
- на `trading.BidPlaced` — `CatalogService.HandleBidPlaced` (отдельная транзакция каталога, обновление лота, возможны новые события каталога → снова outbox).
- на `trading.AuctionClosed` / `AuctionCancelled` / `AuctionWon` — соответствующие методы каталога и сделок.

То есть **«другой домен»** здесь — это не отдельный микросервис, отвечающий по HTTP, а **те же библиотечные use case’ы**, скомпонованные в процессе `integration` с доступом к **той же БД**. HTTP-процесс каталога при этом **не участвует** в обработке `LotPublished` для торгов: об этом узнаёт только `integration`.

### 3.4. Каскад событий и задержка между шагами

- После обработки `LotPublished` в Trading в outbox могут появиться **`trading.AuctionPublished`** и др. Они **не обрабатываются в том же вызове `Publish` шины** для исходного сообщения: их доставит **следующая** (или несколько следующих) итерация `Relay.RunOnce`.
- Практический смысл: между «HTTP вернул 200» и «в БД появился аукцион» есть **зазор** в десятки–сотни миллисекунд (пока `integration` заберёт сообщение). Поэтому в демо-скриптах после публикации лота делают паузу или опрос БД.

### 3.5. Закрытие аукциона без HTTP Trading

Закрытие инициируется:

- **CLI** `cmd/admin close-auction` (отдельный процесс: открывает БД, вызывает `CloseAuction` use case Trading — снова запись в outbox), или
- **планировщик** в `integration` (`RunCloseExpired`), который по списку id из БД вызывает тот же `CloseAuction`.

Дальше цепочка та же: relay → шина → обработчики `AuctionClosed` / `AuctionWon` → use case’ы Catalog и Deals.

## 4. Карта событий и реакций (что подписано в `integration`)

Ниже — фактические реакции в `internal/integration/runtime` после доставки relay’ем.

### 4.1. Публикация лота → аукцион и проекция для сделки

- **Инициатор:** Catalog (HTTP: публикация лота).
- **Событие:** `catalog.LotPublished`.
- **Обработка в integration:**
  - **Trading:** создаётся аукцион по лоту, выполняется публикация аукциона (в рамках правил домена).
  - **Catalog:** при необходимости назначается `auction_id` лоту (если не был задан заранее).
  - **Deals:** создаётся **проекция** связи аукцион ↔ продавец ↔ снимок товара и стартовая цена — чтобы сделка дальше не ходила в Catalog за карточкой товара.

### 4.2. Ставки → обновление каталога

- **Инициатор:** Trading (HTTP: размещение ставки).
- **Событие:** `trading.BidPlaced`.
- **Потребитель:** Catalog — обновление отображаемой цены/состояния по аукциону (через application-слой каталога).

### 4.3. Закрытие / отмена аукциона → каталог

- **События:** `trading.AuctionClosed`, `trading.AuctionCancelled`.
- **Потребитель:** Catalog — согласование отображения лота с итогом торгов.

### 4.4. Победа в аукционе → сделка и каталог

- **Событие:** `trading.AuctionWon` (должен быть непустой победитель).
- **Обработка:**
  - **Deals:** создаётся цепочка выбора победителя / сделки от аукциона (use case создания selection из `AuctionWon`).
  - **Catalog:** фиксация итога (финальная цена, победитель) для лота.

### 4.5. Автозакрытие по времени

- Процесс `integration` дополнительно по таймеру опрашивает БД на предмет **истёкших по времени аукционов** и инициирует **закрытие аукциона** тем же механизмом, что и ручное закрытие (через trading use case `CloseAuction`). Интервал и размер пачки задаются переменными окружения `AUCTION_CLOSE_INTERVAL_SEC`, `AUCTION_CLOSE_BATCH`.

## 5. Как пользоваться системой

### 5.1. Требования

- Docker и Docker Compose (для типового запуска).
- Локально при необходимости: Go **1.22.x** (для `go run`, тестов, утилит).

### 5.2. Запуск через Docker Compose

Из корня репозитория:

```bash
make compose-up
```

или:

```bash
docker compose up -d --build
```

Поднимаются: **PostgreSQL**, однократно **migrate**, службы **catalog**, **trading**, **deals**, **integration**.

**Порты хоста:**

- PostgreSQL: `5433` → `5432` в контейнере (пользователь/БД по умолчанию: `fish` / `fish`).
- Catalog: `8081`
- Trading: `8082`
- Deals: `8083`

Остановка и очистка тома БД:

```bash
make compose-down
```

### 5.3. Проверки и демонстрационные сценарии

- Прогон тестов: `make test`
- Готовые сценарии (bash + curl + при необходимости admin):  
  `make demo-happy`, `make demo-fallback`, `make demo-auto`, либо `make demo-all`

Скрипты лежат в `scripts/` (например, `demo_happy_path.sh`). Типовой happy-path: создание сущностей в Catalog → публикация лота → **ожидание**, пока `integration` обработает outbox и создаст аукцион → ставки через Trading → закрытие аукциона (см. ниже) → проверка строк в БД (сделка, лот).

### 5.4. Минимальная ручная цепочка по HTTP (логика)

1. **Catalog (`8081`):** создать рыбу → продукт → опубликовать продукт → создать лот (заголовок `X-Company-ID`) → опубликовать лот. В теле лота задаются расписание аукциона (`auction_starts_at`, длительность и т.п. — как в API каталога).
2. Дождаться появления записи аукциона в БД (или использовать известный заранее `auction_id`, если назначали вручную через API каталога).
3. **Trading (`8082`):** `POST /auctions/{id}/bids` с заголовками `X-Company-ID`, `X-User-ID` и телом `{"amount": ...}`.
4. **Закрытие аукциона:** в текущей поставке публичного HTTP-метода закрытия у Trading может не быть; используется **либо** фоновый цикл в `integration`, **либо** утилита администратора (см. `docs/admin/README.md`):

```bash
PGHOST=localhost PGUSER=fish PGPASSWORD=fish PGDATABASE=fish PGPORT=5433 \
AUCTION_ID=<auction_id> \
go run ./cmd/admin close-auction
```

5. **Deals (`8083`):** после появления сделки — чтение и переходы по жизненному циклу через HTTP API (`/deals/...`, `/deal-projections/...` — см. маршруты в `internal/deals/http/router.go`).

### 5.5. Важно для эксплуатации

- **Служба `integration` обязательна** для сквозного сценария Catalog → Trading → Deals через события: без неё outbox не будет доставляться подписчикам.
- Relay работает с **общей** таблицей outbox; межсервисная связь здесь — не брокер Kafka/RabbitMQ, а **БД + выделенный воркер**.

## 6. Технологии

| Компонент | Технология |
|-----------|------------|
| Язык и рантайм | **Go 1.22** |
| База данных | **PostgreSQL 15** |
| Драйвер БД | **jackc/pgx/v5** (через `database/sql`) |
| Контейнеризация | **Docker**, **Docker Compose** |
| Сборка образов | многостадийный **Dockerfile** (`golang:1.22-alpine` → `alpine`), бинарь на `cmd/<service>` |
| Миграции | SQL-файлы в `migrations/`, отдельная цель `migrate` в Compose |
| Междоменная доставка событий | **Transactional Outbox** (`internal/infra/outbox`) + **Relay** + **in-memory Event Bus** в процессе `integration` |
| HTTP | стандартная библиотека `net/http`, собственные роутеры по доменам |

## 7. Краткий итог для заказчика

- Реализованы **три домена** (Каталог, Торги, Сделки) как **отдельные сервисы** с **общей PostgreSQL**.
- **Связность** обеспечена **outbox** в БД и сервисом **`integration`**, который доставляет события и **синхронно** вызывает подписчиков, запускающих use case’ы других доменов (подробно — §2–3).
- **Пользовательский и административный сценарии** покрыты HTTP API каталога/торгов/сделок, демо-скриптами, Makefile и CLI `cmd/admin` для операций вроде закрытия аукциона.
- **Стек** — Go, PostgreSQL, Docker; без внешнего брокера сообщений в текущей конфигурации Compose.

При необходимости масштабирования на несколько инстансов outbox-consumer’а или геораспределение потребуется заменить/дополнить in-memory шину транспортом (брокер, HTTP-ретранслятор) с сохранением семантики outbox.
