# ADR-0008: Role-aware UI, Seeded Fish Catalog, and Auction Read Model

## Context
Frontend раньше показывал почти одинаковый рабочий экран для покупателя,
продавца и роли `buyer_seller`. Экран сделки тоже был привязан скорее к общему
lifecycle, чем к стороне пользователя в конкретном контракте.

Справочник рыбы наполнялся вручную через admin UI, поэтому после нового запуска
нужно было заново создавать базовые позиции. В dev/demo окружениях в справочник
также попадали тестовые записи.

Список аукционов на фронте строился в основном из local UI mirror, потому что
Trading не отдавал list endpoint. Из-за этого истекшие аукционы могли
отображаться как `PUBLISHED`, а переход в детали иногда вел к `auction not found`.

## Decision
- Разделить главный frontend screen на три режима:
  - `buyer` — покупательский интерфейс: торги и закупочные сделки.
  - `seller` — интерфейс продавца: продукты, лоты, свои торги и продажи.
  - `buyer_seller` — отображается как «без роли» и сохраняет полный интерфейс.
- Экран сделки определять не по роли аккаунта, а по конкретному контракту:
  - `supplierId == current company` — интерфейс продавца.
  - `customerId == current company` — интерфейс покупателя.
- Добавить seed-миграции для базового fish catalog и отдельную cleanup/expand
  миграцию для удаления известных тестовых записей.
- Оставить frontend fallback catalog, но фильтровать мусорные fish names,
  дедуплицировать список по названию и сортировать его.
- Добавить в Trading query endpoint `GET /auctions`.
- Запустить в Trading background closer, который закрывает истекшие
  `PUBLISHED` аукционы через существующий `CloseAuction` use case, чтобы
  состояние менялось в БД и события продолжали идти через outbox.
- На фронте сначала читать аукционы из Trading API, а local mirror использовать
  только как fallback/demo layer.
- Для старых локальных записей вычислять effective auction state по `endsAt`,
  чтобы просроченный аукцион не показывался как активный.

## Consequences
- Покупатель, продавец и «без роли» получают разные рабочие сценарии без
  дублирования backend ролей.
- Действия по сделке зависят от фактической стороны в контракте, поэтому один и
  тот же пользователь может видеть разные панели в разных сделках.
- Базовая рыба доступна сразу после миграций, без ручного admin bootstrap.
- Старые demo/test fish records не должны попадать в product creation select ни
  из БД после миграции, ни из browser localStorage fallback.
- Trading становится источником списка аукционов, а не только деталей по id.
- Истекшие аукционы закрываются через application/domain path, поэтому catalog,
  deals и projections получают обычные события.
- UI больше не обещает «идет прием ставок» после `endsAt`, даже если frontend
  видит устаревшую локальную запись до полной синхронизации.
